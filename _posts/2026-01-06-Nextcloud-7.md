The final step in the deployment phase is to capture the current state of the server. This ensures that I can quickly recover or scale the infrastructure using Amazon Machine Image(AMI) and a Launch Template. This project focuses on ensuring that the system is not only functional but also resilient and recoverable. 

### 6.1 AMI & Launch Template

To ensure that the server can be replicated or recovered instantly, I captured the entire system state into a image.

AMI: I created an AMI named NextcloudAMI. This is a complete snapshot of the Ubuntu OS, Docker engine, and all pre-configured application settings.

![ami1](/assets/img/aws_cloud/ami1.png)

![ami2](/assets/img/aws_cloud/ami2.png)

![ami3](/assets/img/aws_cloud/ami3.png)

Launch Template: I then built a Launch Template using this AMI. It stores all the necessary parameters—such as the Instance Type, Key Pairs, and the NextcloudSecurityGroup. While the AMI captures the software state, the Launch Template acts as a blueprint for the hardware and network configurations needed for an instant deployment. I specifically did not assign a public IP in the template settings, as I intended to use a fixed Elastic IP for the server to maintain a consistent entry point.

### 6.2 AWS Backup Strategy

To protect the entire stack from data loss, I implemented a centralized backup strategy using AWS Backup. This ensures that both the system state and the application data are secured automatically.

![backup1](/assets/img/aws_cloud/backup1.png)

Backup Plan: I created a plan named NextcloudBackupPlan. I started with the Daily-35day-Retention template and customized it to include a 1-year retention rule.

![backup2](/assets/img/aws_cloud/backup2.png)

Lifecycle Policy: To manage costs, I configured the plan to transition backups to Cold Storage after 3 months.

I created a resource assignment named NextcloudResources. Instead of backing up everything in the account, I manually selected the specific components for this project: 

EC2 Instance: To back up the root system and OS configurations.  
EFS Filesystem: To protect the Nextcloud application metadata and database.  
S3 Bucket: To ensure the primary user data is replicated and safe.

### 6.3 Disaster Recovery Plan

The following workflow outlines how to recover the Nextcloud service in the event of an EC2 instance failure.

**1. EC2 Instance is Terminated or Corrupted**

Prerequisites:  
A pre-configured Launch Template exists.  
An Elastic IP is available.  
EFS and S3 storage remain intact.  

Recovery Workflow:

Launch a New Instance:  
Go to EC2 Console -> Launch Templates.  
Select NextcloudLaunchTemplate and launch the instance.  
The new instance will automatically launch with the custom AMI (Docker is pre-installed and the EFS volume will mount via the User Data script).  

Re-associate the Elastic IP:  
Once the new instance is "Running," go to Elastic IPs.  
Select the Elastic IP -> Associate Elastic IP address.  
Choose the new instance and associate. This keeps the domain connection seamless without needing to update Duck DNS.  

Service Verification:  
Wait a few minutes for the Docker containers to start automatically (configured with --restart always).  
Navigate to the Duck DNS domain. The service should be fully operational with all data and configurations intact.  


**2. Restoring from Backup (In case of Data Loss)**

If the EFS or S3 data is lost or corrupted, I can use AWS Backup to roll back.

EFS Restore:  
Navigate to AWS Backup -> Backup vaults, select the EFS recovery point, and click Restore.  
If a new EFS ID is generated, update the /etc/fstab on the EC2 instance.  

S3 Restore:  
Use S3 Versioning to roll back specific files or perform a full bucket restore through the AWS Backup console.  

EBS Restore (AMI):  
The AMI created previously is the primary recovery method for the server itself. I can launch a new instance directly from this AMI if the Launch Template is unavailable.
